## 一、代码原则（每份 spec 都遵守）

1. **修根因，不打补丁**：不加特判、不绕开症状；同一类问题在一处收口。
2. **功能隔离**：一个模块只管一件事，改动面限定在这件事的边界内。
3. **先复用，再抽象，最后自研**：先找仓库已有的出口，再找成熟库（2–3 个，写明版本、许可证，Shiyu 拍板），都不合适才自己写，并写明理由。
4. **可维护**：抽象只为已存在的重复服务，不为假想需求预留；命名和边界要让下一个人不读历史也看得懂。

## 二、六条规矩

| # | 规矩 | 验收 |
|---|---|---|
| 1 | 事实在**最新 main** 现读，标 commit + 行号；执行方 S0 逐条复核，不成立就停 | spec 有「已查实的约束」；报告有逐条复核 |
| 2 | 「怎么设计」的问题，先给 2–3 个主流方案和取舍，拍板后再写 spec | 先收到方案对比，后收到 spec |
| 3 | 本地只跑受影响文件 + `npm test`，库用 Docker 起的 PG；合并前提是分支 CI 绿；合并本身只做 git 操作，合并后不等 main 的 CI | 报告里没有本地全量数字 |
| 4 | spec 交付 `.md`，放进 `docs/specs/`，补充写进同一文件；参考实现用分支提交交付，不用补丁文件 | 执行方重读文件，不翻会话 |
| 5 | 审计先列改动文件，逐个写结论；没看完不下「通过」 | 审计有逐文件清单 |
| 6 | 本段改动面内新发现的问题直接修；撞车或需拍板才停；不自行记账 | 报告无新增记账，或每条附 Shiyu 同意 |

## 三、spec 写什么

**必备**（每份都有）：
- 头部：前置 spec、参考实现所在分支与提交
- 已查实的约束：事实 + 坐标（`文件:行号 @ commit`）；涉及起环境的，含端口 / 容器 / 数据卷
- 改动：改哪些模块、边界在哪、复用了什么
- 对账表：变异 → 预期红的测试；**作者发出前在交付的那个分支上实跑，有存活不发**
- 测试：一句话，照第 3 条

**按需**（用得上才写，用不上不写）：

| 小节 | 什么时候写 |
|---|---|
| ① 出处对照表 | 照某个规范 / 库的行为实现时（如 APG、RFC） |
| ② 全量扫描原文 | 改动涉及「全仓有多少处」时（选择器、z-index、调用点） |
| ③ 规模表 | 有列表或数据源、数量会影响展示时 |
| ④ 调用点矩阵 | 同一改动影响多个调用点时 |

## 四、skill 用法（每个阶段最多用一个，不叠加）

| 阶段 | skill |
